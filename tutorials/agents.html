🤖 Agents

StarlingAI ships 40+ specialist agents plus ephemeral fallback. The swarm can match reusable workflows first, then route to the right specialist set automatically.

How the swarm routes tasks

You never need to address agents directly. Simply send a message — the swarm analyses it, checks the workflow catalog for reusable scenes or jobs, searches for the best matching specialist using hybrid semantic + outcome-weighted scoring when needed, delegates the task, and returns the result. If the first agent fails, the swarm automatically falls back to the next-best candidate — self-healing without human intervention.

This is the swarm's emergent execution: each delegation improves future routing through outcome tracking, while coordinator agents keep recurring packets reusable through search_workflows and run_workflow instead of rebuilding the same plan every time.

Representative specialist roster

Most default specialists now run on lmstudio/qwen/qwen3.5-35b-a3b. The full catalog lives under workspace/agents; the table below shows representative roles that reflect the current defaults and routing behavior.

Agent Typical use Notes
researcher Fresh web research, documentation lookup, fact-checking SearXNG-first with Playwright and DuckDuckGo fallback; publishes reusable findings
security_researcher CVE lookup, advisories, exploit status, threat intelligence Specialized for NVD, MITRE, vendor bulletins, and patch status research
shell_agent Targeted shell commands, build checks, remote SSH inspection Handles straightforward CLI and server inspection tasks; grounded in exact stdout/stderr
ops_triage Service health, container/log diagnosis, remote host triage SSH-aware and used when requests are about Docker, health checks, logs, or service state
browser_agent Interactive websites, JS-rendered pages, browser evidence capture Uses Playwright-backed tools and secure credential fill instead of typing secrets directly
web_task_coordinator Fresh web tasks that mix research, browsing, evidence, and synthesis Workflow-first coordinator for browser inspection, briefs, and source-grounded packets
mission_coordinator Complex multi-agent missions with dependencies and one final quality gate Prefers reusable workflows first, then delegates the smallest viable specialist plan
code_analyst Workspace inspection, bug diagnosis, architecture review Read-heavy specialist for pinpointing defects and implementation gaps
coder Code changes, refactors, debugging, implementation work Paired with qa_guard when a task needs execution plus verification
document_intake Attachment classification, long-report extraction, normalization Front door for PDF, DOCX, and mixed-attachment workflows
paper_author Source-grounded reports, papers, and long-form technical writing Used after evidence collection, not as a substitute for evidence gathering
quality_supervisor Strict acceptance review and rerun gating Approves complete drafts or names one smallest corrective pass
infrastructure_agent Provisioning, readiness checks, Terraform, Ansible, SSH transfers Used once diagnosis is complete and the task needs actual infrastructure change
computer_use_agent Desktop UI automation through remote VNC/RDP workflows Reserved for actual desktop interaction; not the first choice for headless server tasks
mail_agent Mailbox triage, drafting, reply support across configured accounts Backed by the dedicated mail-service and approval-gated sending flows
productivity_agent Notes, reminders, timers, and durable memory maintenance Best for lightweight follow-up workflows inside the workspace
agent_architect Ephemeral specialist creation when no catalog match clears the threshold Fallback path, not the first option when an existing specialist or workflow already fits
ℹ️
Browser and desktop specialists can use stored credentials without exposing them to the model. browser_agent uses get_site_credentials for metadata and site_fill_credentials for secure browser logins, while computer_use_agent can use computer_type_credential for desktop login forms. Headless server work should route to shell_agent, ops_triage, or incident_responder with ssh_exec instead of desktop automation.
Changing a model for an agent

Via the dashboard

  1. Open http://localhost:3001
  2. Go to Settings → Sub-Agents
  3. Click the agent you want to change
  4. Update the Primary model and optionally the Fallback model fields
  5. Click Save

Via workspace/agents

jsonc
{
  subAgents: {
    researcher: {
      model: {
        primary: "lmstudio/qwen/qwen3.5-35b-a3b"
      }
    },
    summarizer: {
      model: {
        primary: "lmstudio/qwen/qwen3.5-35b-a3b",
        maxTokens: 2048
      }
    }
  }
}
ℹ️
Agent config changes under workspace/agents hot-reload into the running gateway. Restart the container only when you change environment variables, container images, or compose wiring.
Embedding model (better routing)

By default the orchestrator uses keyword matching to route queries. Installing a dedicated embedding model in LM Studio enables semantic search — significantly improving routing accuracy.

Recommended embedding model

Search for text-embedding-qwen3-embedding-0.6b in LM Studio's Discover tab, download it, and load it alongside your main model. Then update your config:

json
{
  "agents": {
    "defaults": {
      "model": {
        "embeddingModel": "text-embedding-qwen3-embedding-0.6b",
        "embeddingBaseUrl": "http://host.docker.internal:1234/v1"
      }
    }
  }
}
Running evaluations

StarlingAI ships with an evaluation harness. Run it to benchmark agent quality and routing accuracy using your own test cases.

Using the canonical eval file

bash
pnpm --filter @starlingai/core agents:evaluate

Writing your own evals

Copy the canonical file and add your own test cases:

bash
cp agent-eval.jsonc my-evals.jsonc
# Edit my-evals.jsonc, then:
pnpm --filter @starlingai/core agents:evaluate my-evals.jsonc
jsonc
// my-evals.jsonc
{
  "workspacePath": "/workspace",
  "cases": [
    {
      "name": "research-docs",
      "agentName": "researcher",
      "task": "Summarise the LM Studio function calling requirements.",
      "expectIncludes": ["LM Studio"],
      "expectExcludes": ["Sub-agent error:"],
      "maxDurationMs": 45000
    },
    {
      "name": "coder-smoke",
      "agentName": "coder",
      "task": "Write a Python function to parse ISO dates.",
      "expectIncludes": ["def"],
      "expectExcludes": ["Sub-agent error:"],
      "maxDurationMs": 30000
    }
  ]
}

The evaluator prints pass/fail summaries, case previews, and can compare the run against a saved baseline.
