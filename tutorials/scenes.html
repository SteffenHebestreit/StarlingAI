🎬 Scenes, Jobs & Automation

Define reusable scenes, chain them into jobs, and let workflow-aware coordinators execute the right packet automatically.

What is a workflow?

A scene is a named, reusable task template that the swarm executes autonomously. A job chains multiple scenes into a reusable multi-step packet. Together they form the workflow catalog that coordinators can search with search_workflows and execute inline with run_workflow before they invent a brand-new plan.

Scenes define the task, participating agents, optional approval gates, and webhook triggers. Jobs add sequencing for recurring packets like deep-research dossiers, source-grounded papers, or visual briefings. You define the goal and the reusable boundaries; the swarm still decides the best specialist execution inside those boundaries.

💡
Think of scenes as missions and jobs as mission packets. Examples in the default workspace include deep_research, source_backed_paper, and the multi-step job daily_ops_brief.
How to create a reusable workflow

Via the dashboard

  1. Open http://localhost:3001
  2. Go to Settings → Scenes → New Scene
  3. Give the scene a name (e.g. daily_report) — no spaces, use underscores
  4. Describe the scene objective in the Task field
  5. Optionally define parameters, allowed agents, and approval-gated tool names
  6. Click Save

Via workspace files

Declare reusable scenes under workspace/scenes and reusable jobs under workspace/jobs for version-controlled automation:

jsonc
{
  scenes: {
    deep_research: {
      description: "Build a source-backed research dossier or design guide on a topic, with optional Mermaid visualizations",
      task: "Run mission_coordinator. Phase 1 - researcher gathers authoritative sources and publishes structured share_finding records. Phase 2 - evidence_analyst reconciles the ledger and resolves conflicts. Phase 3 - paper_author drafts the dossier per the requested deliverable shape, then quality_supervisor runs one acceptance pass.",
      allowedAgents: [
        "mission_coordinator",
        "researcher",
        "evidence_analyst",
        "paper_author",
        "quality_supervisor",
        "summarizer"
      ],
      params: {
        deliverable: { description: "Preferred output shape (dossier, design guide, comparison memo, etc.)", default: "source-backed dossier with Mermaid diagrams where useful" }
      }
    }
  }
}
Triggering a scene

Reusable workflows can be triggered in three ways:

1. From chat

Ask for the outcome in plain language and the coordinator can match a reusable workflow automatically. You can still run a specific scene explicitly with /run:

chat
Create a source-grounded paper comparing the latest MCP and A2A protocol guidance.

/run deep_research

# With variables:
/run deep_research deliverable="comparison memo" audience="engineering leadership"
ℹ️
Plain-language requests can be matched against scenes and jobs in the workflow catalog. Explicit /run commands remain useful when you already know the exact reusable scene you want.

2. Via the REST API

bash
curl -X POST \
  "http://localhost:8765/api/scenes/daily_report/run?key=$SCENE_KEY" \
  -H "Content-Type: application/json" \
  -d '{"params": {"recipientEmail": "steffen@example.com"}}'
ℹ️
The ?key= value is the scene's own webhookKey, set on the scene definition (e.g. webhookKey: "$SCENE_APPLY_JOBS_KEY") and resolved from your environment — it authorizes that one scene, not the whole instance. You can also pass it via the X-Scene-Key header. Alternatively, authenticate with an operator Bearer token (Authorization: Bearer <token>) instead of a key. Keep any key secret.

3. From the dashboard

Open the Chat page and use the scene dropdown in the composer — each scene shows a ▶ trigger. Click it to launch that scene, which runs under your authenticated user. The Settings → Scenes panel is for creating, editing, and deleting scenes (there is no Run button there).

Example: source-backed paper scene

Here's a fuller scene definition that constrains delegation, preserves evidence-first drafting, and keeps the final quality pass explicit.

json5
{
  scenes: {
    source_backed_paper: {
      description: "Produce a paper or report grounded in official sources and verified citations",
      task: "If evidence is still thin or uneven, use mission_coordinator to coordinate the smallest viable evidence-gathering pass with researcher, consolidate findings, draft only from collected evidence with paper_author, and run exactly one final quality pass with quality_supervisor before finalizing.",
      allowedAgents: [
        "mission_coordinator",
        "researcher",
        "paper_author",
        "quality_supervisor"
      ],
      params: {
        outputStyle: { description: "Requested style or citation format", default: "technical report with inline references" }
      }
    }
  }
}
Jobs chain scenes together

Jobs live under workspace/jobs and sequence multiple scenes into a reusable packet. They are the right tool when a request always needs the same multi-phase flow.

json5
{
  jobs: {
    daily_ops_brief: {
      description: "Prepare a verified brief and then distribute it through the configured channels",
      steps: [
        {
          scene: "source_backed_paper",
          label: "Research and verify"
        },
        {
          scene: "multi_channel_broadcast",
          label: "Broadcast summary"
        }
      ]
    }
  }
}
Human-in-the-loop approval

Add approval gates to pause a scene before executing sensitive tools. The orchestrator will send an approval request to your chosen channel and wait for you to confirm before continuing.

json5
{
  scenes: {
    apply_jobs: {
      description: "Submit one approved freelance application",
      task: "Use web_task_coordinator to review one approved lead and delegate browser submission only after stored credentials exist and secure credential fill has been approved.",
      allowedAgents: ["web_task_coordinator", "browser_agent", "researcher", "summarizer"],
      // Pause before executing these tool names
      humanInLoopSteps: ["site_fill_credentials", "mcp__playwright__browser_navigate"],
      // Send approval requests to this channel
      approvalChannel: "slack",
      params: {
        minRating: {
          description: "Minimum lead score to accept",
          default: "0.7"
        }
      }
    }
  }
}

When the scene reaches a tool listed in humanInLoopSteps:

  1. The bot sends you a message on the approvalChannel showing what it's about to do
  2. It waits (up to 24 hours by default)
  3. Reply "approve" to continue, or "reject" to abort the scene
ℹ️
Gate the secret-bearing action, not the lookup. For stored site credentials, use site_fill_credentials or computer_type_credential as the approval step. get_site_credentials returns metadata only.
⚠️
The approvalChannel must be connected and the requesting user must have a valid pairing for that channel. See the Channels guide for setup instructions.
Scene parameters & templating

Scenes use simple double-brace placeholders inside the task string. Values are resolved at runtime from:

  1. Run-time input — provided when triggering via chat or API
  2. Scene defaults — declared in the params section
  3. Inline fallback — the value after the pipe in {{name|default}}
text
Available template variables:

{{recipientEmail}}         — required runtime parameter
{{topN|5}}                 — runtime parameter with inline default
{{minRating|0.7}}          — scene parameter with a fallback value
Webhook-triggered scenes

Add a webhookKey when you want to trigger a scene from another system without an interactive chat session. Keep the key secret and prefer environment-backed values.

json5
{
  scenes: {
    apply_jobs: {
      webhookKey: "$SCENE_APPLY_JOBS_KEY",
      // ...
    }
  }
}
💡
Trigger the scene with POST /api/scenes/<name>/run?key=<webhookKey> and include any parameter values in the JSON body.
